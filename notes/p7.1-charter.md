# P7.1 Runloop-Aware Bench Harness — Follow-Up Charter

Tranche follow-up for the three runloop-dependent P7 exit criteria (§5
#1, #2, #3) that γ's bench harness could not close because Go's `go
test` worker goroutines do not run on OS thread 1 and cannot pump the
main-thread runloop. Opens after the `perf/2026-q2` tag lands. Closes
when the three exits report measured numbers from a running SwiftUI
main loop.

This is explicitly a **small single-agent follow-up**, not a full
tranche. Expected size: one bench harness file + two or three Go-side
benchmarks + optional Instruments walkthrough notes. No new Swift
surface. No charter reframes.

## 1. Problem

P7 landed (a2ui 7a16163) with infrastructure, structural evidence, and
2/5 charter exits PASS. Three exits are blocked on a runloop the Go
bench harness cannot supply:

- **§5 #1**: "Bulk TableModel / rapid slider: no per-row
  `dispatch_async` in Instruments Points-of-Interest." Verification
  requires a running SwiftUI app with Instruments attached; β's
  routing code is verifiable by review, but the Instruments trace is
  the ground truth the charter asked for.

- **§5 #2**: "`examples/bridge-coverage` share/drop scenario shows one
  main-thread hop per (gesture × distinct animation kind) in
  Instruments traces." **Charter defect**: `bridge-coverage` does not
  exercise animated-state setters at all (verified:
  `grep -n Animated examples/bridge-coverage/main.go` returns zero
  hits). The correct flagship is `examples/animation` (slider drag +
  auto-cycle timers emit multiple `SetAnimatedWith` per frame across
  animation curves). This P7.1 tranche corrects the flagship choice
  inline.

- **§5 #3**: "`bridgeCoalesceRatio > 1.5` on the animated-state stress
  bench." γ's `BenchmarkCoalesceRatio` measured the representative
  workload (4 goroutines × 10 writes/frame × mixed kinds) but reported
  `mainHops = 0` because `go test` never pumps the Swift side's
  `DispatchQueue.main.async` flush. `CoalesceUpperBound` at ~205k
  writes/9.3µs tick with `mainHops=0` is structural proof the queue
  coalesces at the bench limit; the reported-ratio number remains
  unreachable from bench context.

## 2. Goal

Close the three P7 exit criteria with numbers from an actually-running
SwiftUI main loop. Not fabricate a ratio; measure it.

- No Instruments automation (Instruments is GUI; scripted Instruments

## 4. Approach

### Runloop-aware bench harness

Use `runtime.LockOSThread` to pin a Go goroutine to OS thread 1, start
a stripped SwiftUI app mode that pumps `CFRunLoopRunInMode` for N
frames at a controlled rate (16ms default for 60 Hz), then returns
control to the Go-side bench harness for before/after counter
sampling.

Sketch:

```go
// Sketch only; P7.1 agent's design call on exact shape.
func benchCoalesceRatioWithRunloop(b *testing.B, writesPerFrame int, frames int) {
    runtime.LockOSThread()
    defer runtime.UnlockOSThread()

    // Initialize bridge + arm animated-state callers.
    state := NewIntState(0)
    defer state.Release()

    SwiftUIDebug.ResetCounters()
    startBefore := SwiftUIDebug.Stats()

    for f := 0; f < frames; f++ {
        for w := 0; w < writesPerFrame; w++ {
            go state.SetAnimatedWith(rand.Int(), randomKind())
        }
        pumpRunloopOnceMillis(16) // drive Swift-side flush
    }

    after := SwiftUIDebug.Stats()
    b.ReportMetric(float64(after.CoalescedWrites - startBefore.CoalescedWrites) /
                   float64(after.MainHops - startBefore.MainHops),
                   "ratio")
}
```

The load-bearing primitive is `pumpRunloopOnceMillis` — it needs to:

1. Run `CFRunLoopRunInMode(defaultMode, 0.016, false)` on the
   locked-main-thread goroutine.
2. Allow the Swift `DispatchQueue.main.async` flush to fire.
3. Return control to Go without entering AppKit event loop.

This pattern exists in the repo already — `examples/` use
`runtime.LockOSThread` plus `CFRunLoopRunInMode` for Swift-app-driving
and for the GC crash fix documented in the project memory. P7.1 reuses
the same pattern scoped to a bench harness.

## 5. Exit Criteria

1. `BenchmarkCoalesceRatioRunloop` reports a ratio > 1.5 on a
   representative workload (4 goroutines × 10 writes/frame × mixed
   kinds × 16ms cadence × 60 frames). If the measured ratio is
   smaller, the charter §7 #1 stop fires retroactively and the tag's
   P7 row updates to explicit MISS with the measured number. Going in,
   γ's structural evidence suggests this will pass comfortably.

2. `go test -race -run=CoalesceRatioRunloop` clean. Runloop-pumping
   harness must not race against the Swift side's dispatch queue.

3. No regression on existing P1–P7 benchmark surface. P7.1 adds
   benches, doesn't modify any.

4. (Optional) Instruments trace of `examples/animation` slider drag
   shows one main-queue hop per (gesture × kind). Attaches to the
   commit as verification of §5 #1 and §5 #2.

## 6. Stop Conditions

Stop P7.1 and report if:

1. The runloop harness cannot close the mainHops=0 gap —
   `CFRunLoopRunInMode` fires but the Swift flush still doesn't
   execute. Root cause would be a missing runloop mode or a thread-1
   assumption the bench can't satisfy. If this happens, P7.1 becomes a
   scope note rather than a measurement tranche, and exit #3 stays as
   "structurally verified, reported-ratio unreachable from bench."

2. The measured ratio is < 1.5 under realistic workload. Per charter
   §7 #1, this triggers reframe: not a P7.1 failure, but a signal that
   the real-world coalescing benefit is smaller than designed. P7 row
   in the rollup updates to explicit MISS with the measured number;
   future coalescing work revisits the charter.

3. `runtime.LockOSThread` + SwiftUI app-mode produces unrelated
   instability (GC frames on the pinned goroutine, AppKit event-loop
   state leaking into Go). The project memory documents a GC crash
   pattern with `app.Run()` that is resolved via manual event loop;
   P7.1 must use the manual event loop path (not `app.Run()`) to
   avoid reintroducing the crash.
